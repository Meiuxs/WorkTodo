# WorkTodo 桌面端低摩擦任务流设计

> 状态：待用户审阅
> 日期：2026-09-22
> 关联设计：`docs/superpowers/designs/2026-09-17-worktodo-ui-design.md`
> 关联现有规格：`docs/superpowers/specs/2026-09-20-sidebar-navigation-design.md`、`docs/superpowers/specs/2026-09-20-task-editor-first-screen-design.md`

## 1. 背景与目标

WorkTodo 已经具备离线任务管理、收集箱、计划视图、任务编辑抽屉、标签、子任务、资料关联、回顾和撤销反馈等基础能力。现有 UX 评审指出，下一步的主要问题不是功能缺失，而是高频任务流仍有不必要的操作摩擦：今日页首屏被摘要内容占用、编辑任务需要显式保存、任务行常用动作隐藏在更多菜单中、侧栏层级仍需稳定收敛。

本规格的目标是把 WorkTodo 优化为桌面 Chromium 环境中的低摩擦执行工具：

1. 用户打开今日页后优先看到“现在要做什么”。
2. 用户编辑已有任务时不再需要寻找保存按钮。
3. 完成、星标和改期等高频动作在任务行上一步可达。
4. 反馈清晰、可恢复，不用遮挡主内容的大型提示。
5. 保持现有离线、本地数据、键盘、无障碍和无第三方依赖约束。

## 2. 范围与正式支持环境

### 2.1 正式支持范围

本次方案只针对桌面 Chromium 扩展页面，正式验收使用常见桌面窗口尺寸，例如 1280×800、1440×900 和 1024×768，并覆盖 200% 缩放下的键盘操作与内容可达性。

移动端不是本产品目标：

- 不新增 FAB、Bottom Sheet、软键盘避让或安全区域处理。
- 不把 390px 视口作为本次设计验收标准。
- 不为了移动端重新组织桌面端快速记录、抽屉或 Toast。
- 现有窄屏 CSS 作为基础防溢出兜底可以保留，但本次不扩展移动端交互承诺。

### 2.2 包含范围

- 今日页首屏层级与进度摘要。
- 已有任务的自动保存。
- 任务行高频操作外露。
- 桌面 Toast 位置与反馈语义。
- 侧栏分组的实现核对与导航层级。
- 对应的单元测试、E2E 测试和设计一致性验收。

### 2.3 不包含范围

- 新建任务的草稿自动保存。
- 月历拖拽改期。
- 中文自然语言日期解析。
- 工作记录富文本编辑器。
- 新的任务领域字段、数据库迁移或权限。
- 图标库、远程字体、CDN 或第三方组件。

## 3. 设计原则与关键决策

### 3.1 已有任务自动保存，新建任务明确创建

已有任务已经拥有稳定 ID、revision 和并发冲突机制，适合在字段变化后自动保存。新建任务尚未拥有 ID，若打开抽屉后立即自动保存，会产生大量空任务或半成品任务，因此新建任务继续使用明确的创建动作。

这一区分必须在界面反馈中说清楚：

- 已有任务显示“保存中 / 已保存 / 保存失败”。
- 新建任务继续显示“创建任务”主操作。
- 快速记录和 Popup 仍然是创建任务的最快入口。

### 3.2 今日页让位给任务列表

今日页的日期、进度和下一步信息仍然保留，但从主内容降为辅助信息：

- 进度摘要与日期放在页面标题区域同一行或相邻区域。
- 进度条使用紧凑横向样式。
- “下一步”只保留一条轻量推荐，不占据大块首屏高度；没有推荐任务时使用简短空状态。
- 逾期任务在今日任务列表上方明确显示。
- 快速记录保持在桌面端顶部，任务列表获得首屏主体空间。

### 3.3 高频动作外露，破坏性动作保持收纳

任务行直接提供：

- 完成或恢复。
- 星标。
- 改期。

取消、复制、编辑和移入回收站等低频动作继续放入更多菜单。永久删除或移入回收站不直接放到普通任务行的外露动作区，避免误触；撤销仍由 Toast 提供。

按钮必须同时提供可见文字或明确的可访问名称，不能只依赖颜色、星形或日期图形表达状态。

### 3.4 侧栏使用结构表达层级

侧栏采用现有分组方向：今天、计划、任务、回顾，以及导航末尾的设置入口。设置使用分隔线和弱化色表达次级关系，不吸底、不新增独立“系统”标签。

本次不引入侧栏图标。当前设计规范已经明确避免零散图标；如果未来引入图标，应作为完整图标系统单独设计，包括语义、线宽、主题和无障碍规则。

## 4. 交互设计

### 4.1 任务编辑器自动保存

自动保存只作用于已有任务。

#### 状态模型

编辑器维护以下状态：

- `currentTask`：最近一次成功保存的任务快照及 revision。
- `draft`：表单当前值。
- `dirty`：draft 是否与已保存快照不同。
- `saving`：是否存在进行中的更新请求。
- `queued`：保存请求进行期间是否产生了更新后的 draft。
- `saveState`：`idle`、`saving`、`saved`、`error` 或 `conflict`。

现有 `taskService.edit(id, changes, revision)` 和仓库 revision 校验继续作为唯一写入边界，不改任务数据模型。

#### 保存时机

1. 表单的 `input` 或 `change` 事件更新 draft 并标记 dirty。
2. 使用约 500ms 防抖等待用户完成连续输入。
3. 若 draft 与已保存快照不同，则使用当前 revision 发起一次更新。
4. 请求期间的新改动不丢弃，标记 `queued`；当前请求完成后继续保存最新 draft。
5. 保存成功后，用服务返回的完整任务和新 revision 更新 `currentTask`。
6. 只有当返回结果对应当前 draft 时，才清除 dirty；否则继续下一轮保存。
7. 抽屉关闭前必须先冲刷待保存改动。保存失败或冲突时抽屉保持打开，用户输入保留。

不对每次自动保存都弹 Toast。保存状态放在标题或表单顶部，只有失败、冲突和恢复动作使用 Toast 或冲突面板提醒，避免反馈噪声。

#### 失败与冲突

- 校验失败：显示字段级或表单级错误，保留抽屉和输入内容。
- 普通保存失败：状态显示“保存失败”，提供“重试”；焦点落到状态说明或第一个错误字段。
- revision 冲突：保留现有冲突面板，提供“载入最新版本”和“保留为新任务”两个出口；本地 draft 不得静默丢失。
- 用户关闭时仍有未保存改动：先完成冲刷；无法保存时不关闭抽屉。

### 4.2 任务行快捷动作

任务行使用现有事件委托和控制器动作通道，优先复用既有服务动作，避免为每种按钮建立平行数据流。

- 完成：继续使用行首圆环，已完成任务提供恢复语义。
- 星标：在行尾或操作区直接切换，Toast 说明“已加星标”或“已取消星标”。
- 改期：直接打开已有的日期快捷选项，保留自定义日期入口在编辑抽屉中。
- 更多：保留取消、复制、编辑、移入回收站等低频动作。

任务行空间不足时，优先保持标题、状态和计划信息可读；快捷动作可以在桌面窄窗口下收纳回更多菜单，但不得导致横向溢出或遮挡标题。

### 4.3 今日页信息层级

今日页按以下顺序组织：

1. 页面标题、日期和紧凑进度摘要。
2. 桌面快速记录入口。
3. 逾期任务提示或任务组。
4. 今日任务列表。
5. 下一步轻量推荐或折叠信息。
6. 已完成任务区域。

进度信息不能重复表达同一件事：标题摘要负责数字，进度条负责比例，任务列表负责具体行动。没有任务时使用简短空状态并保留快速记录入口。

### 4.4 Toast

Toast 统一放在桌面窗口右下角，并避开页面边缘的必要间距。它必须：

- 不覆盖当前列表底部的主要操作。
- 有撤销动作时保持撤销按钮可达。
- 使用 `role="status"` 或现有等效语义。
- 在浅色和深色主题下满足现有对比度要求。
- 对自动保存只报告失败、冲突或恢复，不报告每次成功保存。

## 5. 数据流与组件边界

### 5.1 编辑器与控制器

`src/dashboard/task-editor.js` 负责表单 draft、保存状态、防抖、关闭前冲刷和冲突 UI；`src/dashboard/index.js` 或现有控制器回调负责调用 `editTask`，不在视图层直接访问仓库。

保存成功后沿用现有 `TASK_CHANGED` 广播和局部刷新机制，确保其他 Dashboard 或 Popup 页面能收到变化。编辑器自身使用服务返回的完整任务更新 revision，避免下一次保存继续使用旧 revision。

### 5.2 今日视图

`src/dashboard/views/today-view.js` 继续负责今日任务查询、统计和下一步数据；布局变化集中在视图模板与 `src/dashboard/index.css`，不复制任务查询逻辑。

### 5.3 任务行

`src/dashboard/task-list.js` 继续负责任务行标记、可访问名称和动作委托。快捷动作调用已有 `onAction`，由 Dashboard 控制器统一执行服务操作、广播和刷新。

### 5.4 侧栏与反馈

侧栏结构继续由 `src/dashboard/index.html` 表达，路由和角标逻辑不改变。Toast 的生命周期和主题处理沿用现有实现，只调整位置、占位和自动保存相关语义。

## 6. 测试与验收

### 6.1 单元测试

新增或更新以下覆盖：

- 自动保存防抖只提交最新 draft。
- 保存请求期间的连续修改不会丢失。
- 保存成功后 revision 更新并可继续编辑。
- 关闭前会冲刷待保存改动。
- 保存失败保留 dirty 和输入。
- 冲突状态不静默覆盖本地 draft。
- 新建任务仍由明确创建动作提交，不触发已有任务自动保存流程。

### 6.2 E2E 测试

新增或更新以下场景：

- 打开已有任务、修改标题或日期、关闭后重新打开，改动已保存。
- 连续快速修改多个字段，最终状态完整保存。
- 保存失败时抽屉仍打开且输入保留。
- 两个页面同时编辑时仍显示冲突恢复入口。
- 任务行可一步完成、星标和改期。
- 今日页首屏优先显示任务列表，进度摘要保持紧凑。
- Toast 位于右下角且不遮挡任务内容。
- 1024px、1280px、1440px 桌面视口和 200% 缩放下无横向溢出、焦点可达。

现有移动视口测试不再作为新增功能的验收标准。若桌面布局改造自然影响现有窄屏断言，应只保留基础不崩溃和无数据损坏保障，并同步更新测试意图，不能把移动端重新扩张为产品范围。

### 6.3 回归要求

在修改运行时代码或 Manifest 后必须运行：

1. `npm test`
2. `npm run package`
3. `npm run verify:package`

完成后使用 `npm run preview:edge` 验证桌面扩展页面，重点检查自动保存、冲突恢复、Toast、深色主题和键盘路径。

## 7. 实施分期

### 第一阶段：核心任务环

- 编辑器已有任务自动保存。
- 今日页首屏压缩。
- 任务行完成、星标、改期快捷动作。
- Toast 位置和自动保存反馈。
- 对应测试与桌面视口验收。

### 第二阶段：导航与回顾体验

- 核对并收敛侧栏分组实现。
- 完善逾期、进行中、优先级的文字与色彩语义。
- 将工作记录原始文本改为结构化报告。
- 优化设置页快捷键的查阅密度。

### 第三阶段：计划能力增强

- 月历拖拽改期。
- 键盘可访问的改期替代路径。
- 日历任务过多时的展示策略。
- 离线自然语言日期解析可行性评估。

第三阶段不应阻塞前两阶段，也不应与自动保存共用同一轮发布范围。

## 8. 风险与取舍

1. 自动保存会放大并发冲突出现的频率，因此必须优先复用现有 revision 和冲突恢复机制，不能采用静默覆盖。
2. 自动保存成功提示过多会制造噪声，因此成功状态使用编辑器内联状态，Toast 只用于异常和恢复。
3. 任务行直接暴露动作会增加横向压力，因此允许桌面窄窗口回退到更多菜单，但不能牺牲标题和状态信息。
4. 不支持移动端可以显著降低布局复杂度，但正式验收必须明确限定为桌面环境，避免后续把未优化的窄屏行为误认为产品承诺。
5. 日历拖拽和自然语言解析都涉及较高的交互与错误处理成本，后置可以避免第一阶段偏离“记录—查看—处理—保存”主线。
