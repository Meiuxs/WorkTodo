## 1. 修订目标

本版本在保留“个人任务中心 + 工作日历 + 工作记录 + 工作统计”定位的基础上，解决三个问题：

1. 首发范围过大，影响稳定交付；
2. 任务、延期、重复、删除与统计的规则不够精确；
3. `chrome.storage.local` 不适合独自承载长期任务历史与自动快照。

本规格以“先形成可靠的每日工作闭环，再逐步增强”为原则。首发版本的成功标准不是功能数量，而是用户能在三秒内记录事项、每天清楚看到要做什么、以后查得到做过什么。

---

## 2. 产品定位与边界

### 2.1 产品定位

WorkTodo 是运行在 Chromium 内的单人、离线、本地优先工作管理工具，用同一套任务数据支持：

- 临时事项收集；
- 今日与本周工作安排；
- 逾期事项持续暴露；
- 完成工作留痕；
- 基础周/月回顾。

它不是团队协作、项目排期、在线同步或企业流程系统。

### 2.2 明确不支持

V1.x 不支持账号、多人协作、任务分派、云同步、移动端同步、外部服务、网页内容读取、浏览历史读取、AI 在线服务或第三方网络 API。

---

## 3. 用户与核心场景

### 3.1 目标用户

面向在受限办公环境中使用 Chromium 的单个知识工作者，例如工程技术人员、项目人员、销售、行政及多项目并行人员。

### 3.2 核心任务

1. 收到临时事项时，打开扩展并在三秒内记录；
2. 每天开始工作时，一眼确认逾期、高优先级和今日任务；
3. 对未完成事项做完成、延期或取消处理；
4. 在周末或月底回顾实际完成的工作；
5. 在浏览器重启、离线或扩展后台休眠后，任务数据仍然正确。

### 3.3 体验原则

- **先记录，后整理**：快速新增只要求标题，默认进入收集箱。
- **今日优先**：今日页只服务“现在要做什么”，不堆放统计和低频设置。
- **可恢复**：完成、延期和删除都有短时撤销；删除进入回收站。
- **规则可解释**：日期、统计、重复和延期均能追溯来源。
- **本地且透明**：不产生外部网络请求；数据删除和备份风险明确告知用户。

## 5. 信息架构

工作台左侧导航固定为五组，避免让用户在同一层级面对过多入口：

```text
计划：今天 / 明天 / 本周 / 月历（后两项从 V1.1 开始）
任务：收集箱 / 全部任务 / 逾期 / 已完成 / 回收站（V1.1）
项目：分类列表
回顾：工作记录 / 统计
系统：设置
```

Popup 只承担快速动作：

1. 显示日期与“完成 n / m”；
2. 如有逾期，显示一条明确提示；
3. 展示最多三个最需关注的任务；
4. 提供一行新增和“打开工作台”。

Popup 不展示复杂筛选、完整统计或任务详情编辑。

## 6. 任务领域模型与状态规则

### 6.1 任务生命周期

任务生命周期仅包含：

```text
todo → in_progress → completed
                 └→ cancelled
```

- 新建任务默认 `todo`；
- “开始”仅把状态改为 `in_progress`，不强制记录工时；
- “完成”写入 `completedAt`；
- “取消”写入 `cancelledAt` 与可选原因；
- 已完成或已取消任务可恢复为 `todo`，并清空对应结束时间；
- 删除不是生命周期状态。删除写入 `trashedAt`，任务进入回收站；恢复回收站任务只清空 `trashedAt`，保留原状态；永久删除必须二次确认。

### 6.2 任务核心数据

```text
Task
  id: UUID
  revision: number
  title: string（1–200 字符）
  description: string（可选）
  lifecycle: todo | in_progress | completed | cancelled
  priority: none | low | medium | high
  starred: boolean
  categoryId: string | null
  tagIds: string[]（V1.1）
  scheduledDate: YYYY-MM-DD | null
  firstScheduledDate: YYYY-MM-DD | null
  startTime: HH:mm | null
  dueTime: HH:mm | null
  createdAt / updatedAt: ISO 8601（含时区）
  completedAt / cancelledAt / trashedAt: ISO 8601 | null
  seriesId: string | null（V1.1）
```

所有 ID 必须使用 UUID；任何页面和逻辑均不得以数组下标识别任务。

### 6.3 收集箱与日期

- `scheduledDate = null` 的未删除、未完成任务属于收集箱；
- 首次安排日期时，将该日期同时写入 `scheduledDate` 和不可变的 `firstScheduledDate`；
- 此后调整日期只改 `scheduledDate`，不得改写 `firstScheduledDate`；
- 任务从收集箱安排到日期，不计作延期；
- “今天”按照浏览器系统本地时区和本地日期计算；不提供跨时区同步。

### 6.4 时间字段校验

- 时间均使用 `HH:mm`；日期均使用 `YYYY-MM-DD`；
- 无日期的收集箱任务不得设置开始时间或截止时间；
- 同一天存在开始和截止时间时，截止时间不得早于开始时间；
- 跨天工作在 V1.x 不建模为单任务跨日时段；应拆成两项，或仅记录计划日期与描述。

### 6.5 延期与重新安排

用户在任务详情中可以修改日期；只有选择“延期”快捷操作时才产生延期事件。

```text
TaskEvent
  id, taskId, type, occurredAt
  POSTPONE 时额外记录 fromDate、toDate、reason（可选）
```

快捷延期：明天、后天、下周一、下周、自定义日期。目标日期必须晚于当前 `scheduledDate`；若用户选择更早日期，界面称为“重新安排”，而非“延期”。

### 6.6 分类、标签与子任务

- V1.0 每个任务最多一个分类；分类删除时必须先选择“转为未分类”或“转移到另一分类”，不得连带删除任务；
- 标签在 V1.1 采用独立实体与 `tagIds` 关联，避免标签改名后产生重复文本；
- 子任务在 V1.1 单层嵌套，不支持子任务的子任务；父任务完成且仍有未完成子任务时，必须弹出确认，不自动完成子任务。

### 6.7 重复任务（V1.1）

重复任务使用“模板 + 实例”模型，不在一个任务上直接叠加未来日期：

```text
RecurringTemplate → 生成 Task 实例
```

- 支持每天、工作日、每周、每月、每年和有限的自定义规则；
- 默认在当前实例完成后生成下一个实例；
- 实例记录 `seriesId` 与唯一 `occurrenceKey`，同一 occurrenceKey 至多生成一次；
- 取消某次实例不自动取消整个模板；停用模板不影响既有实例；
- 未完成的重复实例不自动批量补齐，避免积压大量历史任务。

## 7. 核心功能需求

### 7.1 快速新增

- Popup 与工作台均提供固定、可聚焦的输入框；
- 输入标题并按 Enter 后立即保存到收集箱；
- 用户可在保存前通过快捷按钮选择今天、明天、指定日期；
- 保存成功后显示短提示与“撤销”；保存失败必须保留输入内容并显示可执行的错误说明；
- 只有当焦点不在输入框、多行描述或日期控件中时，页面级快捷键才生效。

### 7.2 今日页

今日页显示：

1. 逾期且未完成、未取消、未删除的任务；
2. `scheduledDate` 为今天的任务；
3. 已完成任务默认折叠；
4. 排序：逾期优先、星标、优先级、开始时间、创建时间。

今日页默认只显示少量任务统计；不应把月度图表、设置或全部分类同时放在首屏。

### 7.3 逾期、完成与取消

逾期条件：`scheduledDate < 今天`，且 `lifecycle` 不为 `completed` 或 `cancelled`，且 `trashedAt` 为空。

用户可以从逾期列表直接完成、延期、取消或打开详情。取消任务不计入完成率，且不会继续出现在逾期列表。

### 7.4 查询与筛选

V1.0 搜索任务标题与描述，支持状态、计划日期范围、分类、优先级、星标筛选。筛选条件必须可见、可单独清除，并提供“一键清空全部筛选”。

### 7.5 导入、导出与恢复

导出 JSON 至少包含：`schemaVersion`、`appVersion`、导出时间、任务、分类、设置和任务事件。

导入流程必须为：

```text
选择文件 → 格式/版本校验 → 显示数量与冲突预览 → 用户确认覆盖或合并 → 执行并报告结果
```

- 导入校验失败时不得改变现有数据；
- 合并以 UUID 判断同一记录；同一 UUID 内容冲突时，默认保留本机较新 `updatedAt` 的版本，并在结果页报告冲突数；
- 覆盖导入前必须生成一次本机恢复点；
- 扩展卸载会清除扩展本地数据，因此设置页需显示“最近一次导出时间”，并在用户进入数据管理页时提示先导出备份。

## 8. 工作记录与统计口径

### 8.1 工作记录

“某日完成了什么”只按 `completedAt` 的本地日期计算，不按计划日期计算。已取消和已删除任务默认不进入工作记录。

### 8.2 统计定义

| 指标 | 计算口径 |
| --- | --- |
| 新增任务数 | `createdAt` 落在统计区间的任务数 |
| 实际完成数 | `completedAt` 落在统计区间的任务数 |
| 延期次数 | `POSTPONE` 事件发生在统计区间的次数 |
| 计划任务数 | `scheduledDate` 或计划事件落在统计区间的任务实例数 |
| 本周计划并完成 | 首次或当前计划在本周，且在本周完成的实例数 |
| 历史延期到本周完成 | `firstScheduledDate` 早于本周，且在本周完成的实例数 |
| 完成率 | 实际完成数 ÷（统计区间内计划任务数 − 取消任务数） |

分母为零时显示“暂无计划”，不显示 0%。所有统计页必须同时标明“按计划”还是“按实际完成”，避免误读。

### 8.3 规则模板总结（V1.1）

周/月总结只根据已定义指标和任务标题生成，不请求网络或 AI 服务。输出支持复制文本，不自动发送或上传。

## 9. 数据、架构与并发要求

### 9.1 存储分层

| 数据 | 存储位置 |
| --- | --- |
| 任务、分类、标签、事件、搜索索引 | 浏览器内置 IndexedDB |
| 设置、schemaVersion、轻量 UI 状态、最近导出时间 | `chrome.storage.local` |
| 运行期缓存 | 内存或 `chrome.storage.session`，不得作为唯一数据来源 |

IndexedDB 属于浏览器内置能力，不需要独立数据库软件、服务器、管理员权限或网络。任务、事件与分类应使用独立对象仓库，并为 `scheduledDate`、`lifecycle`、`completedAt`、`categoryId`、`trashedAt` 建立索引。

### 9.2 服务边界

页面不得直接读写浏览器存储。统一通过：

```text
UI → TaskService / SearchService / StatisticsService / BackupService
   → TaskRepository / SettingsRepository
   → IndexedDB / chrome.storage.local
```

- 单次修改必须采用事务；
- 每条任务携带 `revision`，Popup 和 Dashboard 同时编辑同一任务时应检测陈旧写入并提示用户刷新或合并；
- 操作完成后通过统一变更通知刷新其他打开界面；
- 服务工作线程重启后必须从持久化存储重新加载必要状态，不依赖全局变量。

### 9.3 数据迁移

每次结构变更提升 `schemaVersion` 并提供向前迁移函数。升级失败时保留原数据、写入可诊断日志，并提示用户导出备份后重试；不得静默清空数据。

## 10. 提醒与后台行为（V1.2）

- 每个提醒只保存任务 ID、目标时间和提醒规则，任务本身是唯一事实来源；
- 扩展启动、浏览器启动和服务工作线程被唤醒时，应检查并重建必要提醒；
- 设备睡眠期间不会被提醒唤醒，醒来后对已错过提醒按“补发一次”策略处理；
- 浏览器完全退出时不承诺系统级准时通知；设置页必须说明该限制；
- 通知不可用、权限被拒绝或创建失败时，任务不丢失，界面提示用户在浏览器设置中检查通知权限；
- 不为每个任务创建高频轮询；优先调度下一个待提醒时间。

## 11. 安全、隐私与权限

### 11.1 安全原则

- 不发起业务网络请求；
- 不声明 `host_permissions`，不读取网页内容、历史、密码、Cookie 或剪贴板；
- 不加载远程 JavaScript、CSS、图标或 CDN 资源；
- 所有代码和静态资源均随扩展离线部署；
- 不记录任务内容到控制台生产日志。

### 11.2 权限策略

V1.0 原则上仅需 `storage`。后续能力按需增加：

| 权限 | 使用时机 |
| --- | --- |
| `alarms` | 启用任务或工作日提醒时 |
| `notifications` | 启用浏览器通知时 |
| `downloads` | 仅当导出必须调用 `chrome.downloads` API 时；否则评估免该权限的导出方案 |
| `unlimitedStorage` | 仅在容量评估证明必要且部署策略允许时申请 |

每个新增权限都必须有对应功能说明与验收用例。

## 12. 可用性与无障碍要求

- 所有核心操作可通过键盘完成；焦点样式始终可见；Esc 可关闭非破坏性浮层；
- 任务状态、优先级和逾期不能只靠颜色区分，必须有文字、图标或辅助说明；
- 正常文字满足 WCAG AA 对比度，交互目标应有足够点击区域；
- 弹窗打开时焦点进入弹窗，关闭后回到触发元素；
- 空状态必须提供下一步操作，例如“今日暂时没有待办，添加任务”；
- 删除、导入、清空等高风险操作给出后果说明与取消入口；
- 快捷键：V1.0 支持 Enter 保存、Esc 取消/关闭；N、F、T、W、M 等页面快捷键在 V1.1 增加，并提供快捷键说明。

## 13. 性能与兼容性要求

- Chromium 110+、统信 UOS、ARM64 为首要验收环境；
- 无网络时，新增、编辑、删除、查询、统计、备份与恢复均可用；
- 常规首次打开应尽量在 1 秒内展示基础界面；
- 在 1,000、5,000、10,000 条任务数据下，今日页、搜索、基础统计和 JSON 导出不得出现无响应；
- 搜索和统计使用索引与增量计算，不在每次输入时全量重建历史；
- 对长标题、超长描述、Emoji、特殊字符、粘贴的多行文本和非法导入文件有明确处理。

## 13.1 测试策略与质量门禁

- 单元测试使用 Node.js 20+ 内置 `node:test`，覆盖领域模型、日期与时区规则、事件模型、IndexedDB 仓库合约、revision 冲突、任务/分类服务、查询排序、统计、备份导入导出以及 Popup/Dashboard 控制器。
- 每个领域或服务任务必须先写失败测试，再写最小实现；修复缺陷时必须补充回归测试。单元测试不得依赖网络、真实用户目录或未隔离的持久化数据。
- E2E 测试使用仅供开发测试的 `@playwright/test`，在隔离的 Chromium 持久化上下文中加载未打包扩展；测试运行时拦截并断言无外部网络请求，不改变产品运行时依赖与 Manifest 权限。
- E2E 至少覆盖：Popup 快速新增并在 Dashboard 可见、安排日期并完成后进入工作记录、编辑抽屉的校验与键盘关闭、导入预览/确认与导出、Popup 与 Dashboard 并发编辑的 revision 冲突、扩展/浏览器重启后的数据持久化。
- 测试命令分为 `npm run test:unit`、`npm run test:e2e` 和 `npm test`；提交前必须通过单元测试与 E2E 测试，E2E 失败时不得以手工验收替代。
- E2E 定位优先使用可访问角色、名称和键盘行为；只有在语义定位不足时才增加稳定的 `data-testid`，不得为了测试暴露内部实现细节。

## 14. 验收标准

### 14.1 核心业务

- 标题输入后按 Enter，任务成功持久化；
- 无日期任务进入收集箱，安排日期后离开收集箱；
- 今日、逾期、完成、取消、删除的筛选结果符合状态规则；
- 延期保留 `firstScheduledDate` 和完整延期事件；
- 完成、恢复、取消、回收站恢复均不丢失历史字段；
- 分类删除不会删除任何任务；
- 导入非法文件不会修改本机数据；合并导入能报告冲突；
- 重复任务在 V1.1 中不会生成重复实例；
- 工作记录按实际完成日显示，周/月统计明确区分计划和实际。

### 14.2 可靠性

- 浏览器、扩展或服务工作线程重启后，已保存数据仍存在；
- Popup 与 Dashboard 同时修改同一任务时，不发生静默覆盖；
- 存储配额、事务失败和迁移失败均显示可理解的处理建议；
- 卸载风险与最近导出时间在数据管理页面可见；
- 提醒上线后，睡眠唤醒、浏览器重启和通知权限拒绝均有测试用例。

### 14.3 安全与离线

- Network 面板中正常使用不产生主动外部请求；
- Manifest 不含无关权限或 host permissions；
- 不存在远程脚本、远程样式或 CDN 依赖；
- 断网后核心功能全部正常。

### 14.4 自动化测试

- `npm run test:unit` 通过，且领域、数据、服务和控制器测试覆盖本规格中的状态、日期、并发、导入导出与排序规则；测试结果可重复。
- `npm run test:e2e` 在干净的隔离 Chromium 配置中通过核心用户闭环，并证明扩展不产生主动外部请求。
- `npm test` 串行执行单元测试和 E2E 测试；任一层失败都视为 V1.0 未达到发布门槛。

## 15. 最终体验目标

用户应能形成以下闭环：

```text
临时事项 → 三秒记录到收集箱 → 安排今日/未来日期
→ 完成、延期或取消 → 自动留下工作记录 → 周/月回顾
```

WorkTodo 的首要价值是减少纸质便签、零散文本、聊天提醒和脑内记忆，而不是让用户维护一套复杂系统。任何新增功能都必须证明：它能提升记录、处理或回顾的可靠性，并且不会破坏“今天一眼看清”的体验。
