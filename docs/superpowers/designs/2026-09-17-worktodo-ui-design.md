# WorkTodo v1.6 UX/UI 设计规范

> 状态：当前产品规范
> 更新：2026-09-19
> 适用范围：Popup、Dashboard、任务列表、工作记录、资料收集箱、任务编辑抽屉、确认对话框、Toast、空/错/成功状态
> 关联实现：`src/styles/tokens.css`、`src/popup/`、`src/dashboard/`

这份文档是 WorkTodo 的 UX/UI 共同约束。UX 决定用户先做什么、如何完成任务以及如何恢复；UI 决定这些路径如何被看见、操作和理解。新增页面或组件必须先回答对应的用户问题，再选择视觉组件。

## 1. 产品定位与设计目标

### 1.1 用户与场景

WorkTodo 面向在受限办公环境中使用 Chromium 的单人知识工作者，例如工程技术、项目、销售和行政人员。他们经常在会议、邮件或浏览资料的间隙想到一件事，需要用几秒记下，然后在合适的时间整理、推进和回顾。

### 1.2 核心问题

用户打开 WorkTodo 时通常只需要回答三个问题：

1. 现在最该推进什么？
2. 新想到的事情放在哪里最合适？
3. 我完成了什么，下一步还剩什么？

### 1.3 体验目标

- **三秒记录**：首次记录只需要标题和一次 Enter，不强迫用户立即分类、安排时间或填写描述。
- **一眼看清**：今日页优先呈现逾期、下一步和完成进度，低频内容后置。
- **逐步展开**：先完成最小动作，再通过抽屉、详情和报表逐步补充信息。
- **行动可恢复**：完成、延期、取消、删除和导入等动作都提供清楚反馈、撤销或恢复路径。
- **本地可信**：明确说明数据存储、保存失败、导入风险和恢复方式，不使用技术错误码吓阻用户。
- **离线可用**：核心记录、完成、延期、回顾和数据操作不依赖网络。

### 1.4 品牌与审美方向

WorkTodo 的审美是 **清透网格**：薄荷灰画布、暖白工作面、深墨绿文字、青绿色行动色、橙珊瑚色提醒。使用结构化网格、细边界和轻微层级差建立秩序，不使用霓虹渐变、玻璃拟态、发光装饰或装饰性卡片堆叠。

界面应该让工作有向前推进的感觉，但不制造紧张感；文案直接、短促、有行动指向。

## 2. UX 信息架构

### 2.1 页面职责

| 入口 | 用户问题 | 页面职责 | 不应该承担 |
| --- | --- | --- | --- |
| Popup | “我现在想到什么？” | 快速记录、显示少量今日重点、提供工作台入口 | 完整编辑、复杂筛选、长表单 |
| 今天 | “现在最该推进什么？” | 逾期、下一步、今日进度、快速记录 | 月度分析、资料管理 |
| 明天/本周/月历 | “接下来怎么安排？” | 计划日期、周节奏、月度分布 | 临时记录的复杂编辑 |
| 收集箱/全部任务 | “我有哪些事项？” | 找回、搜索、筛选和批量理解任务 | 用弹窗承载整页任务浏览 |
| 工作记录 | “我实际完成了什么？” | 周/日回顾、完成节奏、统计和明细 | 把总结编辑器作为首屏主内容 |
| 资料收集箱 | “上下文资料放在哪里？” | 保存、搜索、关联和下载资料 | 强迫用户在记录任务时填写资料 |
| 设置 | “数据如何保存和迁移？” | 主题、导入、导出、分类管理 | 把危险操作做成无确认的一键动作 |

### 2.2 主路径

```text
想到事项 → Popup/快速记录 → 收集箱
        → 需要安排时选择日期或打开任务抽屉
        → 今日页完成/延期/取消
        → Toast 告知结果并提供撤销
        → 工作记录按实际完成日期回看
```

每个页面只保留一个主要推进方向。页面上的次级动作可以存在，但不能和主动作使用同等视觉重量。

### 2.3 信息优先级

Dashboard 今日页固定采用以下顺序：

1. 页面标题和当前日期；
2. 快速记录入口；
3. 逾期事项；
4. 今日待推进事项；
5. 完成进度与已完成折叠区；
6. 低频管理或辅助信息。

工作记录固定采用以下顺序：

1. 本段结论；
2. 完成率和四项核心指标；
3. 工作节奏或今日回顾；
4. 规则模板总结（按需生成）；
5. 实际完成明细。

### 2.4 状态保存范围

工作台是扩展内的单页界面，不使用 URL 或 hash 记录路由与筛选：

- 页面内切换路由时，各视图自己保留筛选条件与日期选择。
- 重新打开工作台或刷新后回到“今天”，不要求恢复上一次筛选。
- 这个取舍必须在验收时说明；如果将来需要可分享或可恢复的视图状态，再引入 URL 参数。

## 3. 视觉系统

### 3.1 颜色语义

颜色只表达稳定的产品语义，不用颜色替代文字和结构：

| 令牌 | 用途 | 语义 |
| --- | --- | --- |
| `--canvas` | 页面背景 | 环境层 |
| `--surface` | 普通内容面 | 内容层 |
| `--surface-raised` | 输入、浮层、主动卡片 | 抬高一层 |
| `--ink` | 标题、正文、主要操作文字 | 主要信息 |
| `--muted` | 辅助说明、时间、低频信息 | 次要信息 |
| `--line` / `--line-strong` | 分隔线、控件边界 | 结构和可操作边界 |
| `--teal` / `--teal-soft` | 主行动、完成、正向进度 | 可以推进 |
| `--coral` / `--coral-soft` | 逾期、删除风险、需要注意 | 需要确认 |
| `--overlay` | Dialog/抽屉背景遮罩 | 当前焦点在浮层 |

浅色和深色令牌统一维护在 `src/styles/tokens.css`。业务样式不得重新定义相同语义的颜色，也不得直接使用纯黑或纯白作为大面积背景。

### 3.2 排版层级

- 字体使用系统中文字体栈，不加载远程字体和 CDN。
- 正文使用 `14px`；界面辅助文字使用 `12–13px`；Popup 标题使用当前 `24px` 主题级标题，Dashboard 主标题使用 `30px` 主题级标题。
- 标题使用清楚的字号差异和 `text-wrap: balance`；正文使用 `text-wrap: pretty`，避免中文孤字。
- 数量、日期和时间使用 `font-variant-numeric: tabular-nums`，减少数据变化造成的跳动。
- 省略号使用中文排版的 `…`，加载文案统一使用“正在加载…”，不使用三个句点。
- 文案不重复解释已经在标题中表达的信息；按钮名称要描述动作，例如“保存任务”“移入回收站”，不使用单独的“继续”“确定”作为主要动作。
- 界面文案只对用户说话：不写实现细节、模块依赖或“与某页规则一致”这类内部约定。需要解释产品规则时，写进本文档或 README，不要占用页面说明行。
- 被单行截断的文本必须能取回全文：允许展示两行，或提供 `title` 属性、详情入口；不得让用户在界面上永远看不到完整标题。

### 3.3 间距、尺寸与层级

- 基础间距以 `4px` 为刻度，优先使用 `8 / 12 / 16 / 20 / 24 / 32px`。
- 普通输入和按钮使用统一控件高度；Popup 主输入使用更高一级的控件高度，确保首屏主入口明显。
- 圆角只用于表达控件或浮层边界：输入和按钮使用小圆角，面板使用中等圆角，不把每一行都包成卡片。
- 阴影只用于抽屉、Popup 浮层和 Toast；普通内容优先使用留白和 1px 边线。
- 主内容列保持可读宽度并左对齐，不为了“居中好看”牺牲连续阅读。

## 4. 核心组件规范

### 4.1 Popup：三秒记录

Popup 目标宽度为 `360–380px`，高度随内容变化。结构固定为：

```text
今日日期                         ↗ 工作台
记下下一件事
快速记录 · 只写标题，稍后再整理
完成进度
逾期/今天要推进
标题输入框                         ＋
[今天] [明天] [收集箱]
成功反馈（需要时出现在内容流中）
```

交互规则：

- 打开后焦点进入标题输入框；这是 Popup 中唯一默认自动聚焦的主输入。
- 只输入标题即可保存；默认进入收集箱，日期按钮是可选增强动作。
- Popup 最多显示少量重点任务，超过范围通过“打开工作台”处理。
- “打开工作台”是文字型次级入口，不和“添加任务”争夺主行动层级。
- 成功 Toast 必须位于内容流中或有明确安全偏移，不能覆盖日期按钮、输入框或提交按钮。
- 成功反馈至少说明“发生了什么”和“下一步可以做什么”；需要撤销时显示可操作的“撤销”按钮。

### 4.2 Dashboard 快速记录

- 输入框是 Dashboard 的稳定主入口，标题是唯一必填字段。
- 计划日期、更多字段和资料关联采用渐进披露，不把完整表单塞进首屏。
- 提交按钮保持可见且使用主行动色；提交期间反馈状态，失败时保留原输入并给出下一步。
- 快速记录区域不得被 Toast、菜单或其他 sticky 元素覆盖；键盘焦点移动时也必须保持可见。

### 4.3 任务行

任务行是高频浏览单元，不是卡片集合。每行可以包含：

- 原生 checkbox 或等价键盘控件；
- 任务标题；
- 计划日期/时间或“无时间”；
- 优先级、逾期、延期等文字状态；
- 悬停或键盘聚焦后出现的次级操作。

状态必须同时使用文字、结构或控件状态表达：

| 状态 | 视觉 | 文字/行为 |
| --- | --- | --- |
| 待办 | 普通文字、空心控件 | 可完成、延期或打开详情 |
| 进行中 | 青绿色轻强调 | 显示“进行中” |
| 已完成 | 低对比度、完成时间 | 可恢复，不能只依赖删除线 |
| 已取消 | 灰化 | 显示“已取消” |
| 逾期 | 珊瑚色小范围强调 | 显示“逾期”和原计划日期 |

### 4.4 任务编辑抽屉

抽屉适合编辑任务，不适合快速记录：

- 从右侧进入，桌面宽度约 `420px`，窄屏使用可用全宽。
- 首屏字段只放任务名称、计划日期、优先级和分类。
- 描述、开始时间、截止时间、重复规则和资料放入折叠或次级区域。
- 底部固定“取消”和“保存任务”，抽屉主体独立滚动，并使用 `overscroll-behavior: contain`。
- 打开后焦点进入任务名称；Esc 和取消关闭，焦点回到触发元素。
- 保存失败不关闭抽屉，不清空输入；并发冲突提供“保留为新任务”和“载入最新版本”。

### 4.5 确认对话框

确认框只用于不可逆、风险较高或需要用户明确选择的动作：删除、永久删除、覆盖导入、移入回收站、仍然完成父任务等。

- 统一使用产品内 `dialog`，禁止新增浏览器原生 `window.confirm`。
- 标题直接说明风险，例如“删除资料？”“覆盖本机数据？”。
- 说明文字解释影响和恢复可能性；不显示技术错误码。
- 危险按钮使用明确动作名称，例如“删除资料”“确认覆盖并导入”，不使用“确认”。
- 默认焦点优先落在取消/安全动作；用户按 Esc 可以取消。
- 对话框宽度不超过视口，长内容在内部滚动，不能让背景页面跟随滚动。

### 4.6 资料表单对话框

- 用于添加资料、关联任务等短流程；每个字段有可点击标签或 `aria-label`。
- 根据资料类型只显示相关字段，避免让用户阅读无关表单。
- 失败信息贴近字段或表单底部，并保留用户已输入内容。
- 窄屏或内容过长时限制在视口内滚动；操作按钮和内容之间使用边线区分。
- 本地文件、网页链接、文本片段的说明必须告诉用户保存方式和大小边界。

### 4.7 Toast 与异步反馈

Toast 是非阻塞反馈，不代替页面状态，也不承担确认动作：

- 使用 `role="status"` 或等价的 `aria-live="polite"`，让读屏用户能收到结果。
- 文案先说结果，再说可选动作；例如“已移入回收站 · 撤销”。
- 默认显示约 5 秒，危险或需要用户处理的错误应留在相关字段或页面，而不是只闪过 Toast。
- Toast 不得遮挡输入、日期按钮、快速记录、底部菜单和当前焦点。
- 进入/退出只使用 `opacity` 和 `transform`；遵守 `prefers-reduced-motion`。

### 4.8 任务行“更多”菜单

次级操作只在需要时展开，避免任务行变成按钮集合：

- 触发器是原生 `<details>/<summary>`，`summary` 提供 `aria-label="更多任务操作"`，Enter/Space 可展开。
- 菜单内按“常用 → 次要 → 危险”排序：开始/完成/取消/星标、日期、优先级、编辑任务（子任务、标签、更多字段）、复制、移入回收站。
- 日期区块使用固定预设：今天、明天、后天、下周一、下周、自定义日期、移除计划日期；预设文字必须带具体日期，避免用户自己换算。
- 优先级区块使用无、低、中、高四档，当前值用 `aria-pressed` 标记。
- 任务行获得焦点时，`D` 打开日期区块、`P` 打开优先级区块的首个按钮，不与全局导航快捷键冲突。
- 菜单限高可滚并 `overscroll-behavior: contain`；窄屏可以贴底展示，但必须能关闭，且不得遮挡当前焦点。
- 窄屏、键盘和指针必须触达同一组动作；不得用 `display: none` 让某一端失去完成、延期或删除能力。

### 4.9 侧栏数量角标与快捷键提示

- 角标只复用目标页面已有的数字（今天页逾期数、收集箱总数），不引入新的状态口径。
- 角标本身 `aria-hidden`，不参与按钮的可访问名称；数字通过按钮的 `aria-describedby` 交给读屏，例如“3 项逾期待处理”。
- 数量为 0 时角标隐藏，导航项名称与排序保持不变。
- 快捷键提示（`kbd`）只标注已经实现的快捷键，含全局导航（T/W/M）、快速记录（N）和搜索（F）；按钮上用 `aria-keyshortcuts` 声明，提示本身 `aria-hidden`。

## 5. 状态与 UX 文案

### 5.1 空状态

空状态必须回答“这里为什么为空”和“下一步做什么”，并且全产品共用同一结构与同一组件（`.empty-state`）：

```text
[标题]  当前状态        “今天还没有待办”
[说明]  原因或口径      一句话，可选
[动作]  唯一主入口      “记录第一件事”，可选
```

- 结构规则：标题一行、说明一行；只有确实存在可执行动作时才加按钮，且只加一个。
- 组件规则：页面级空状态统一使用 `.empty-state`；`.empty` 只用于行内或单元格级提示（月历格、子任务列表、某个日期没有任务）。
- 同一屏只保留一处空状态：标题统计行与空状态卡片不得重复表达同一件事。
- 方位必须真实：文案里的“上方/下方”要与实际布局一致，否则改成不带方位的说法。
- 各页口径：今天无任务用“今天还没有待办”，明天/本周无计划用“明天还没有计划/本周还没有计划”，收集箱为空说明“想到的事情先放进来”，工作记录无数据显示“还没有完成记录”而不是 `0%`，资料为空要提供“添加资料”，回收站为空说明删除的任务会在这里等待处理。

### 5.2 加载与错误

- 加载文案使用“正在加载…”等带省略号的进行时表达。
- 错误文案包含问题和下一步，例如“任务没有保存。你的输入还在，请检查标题后重试。”
- 异步请求失败不能产生未处理 rejection，也不能用迟到的旧请求覆盖当前页面。
- 表单错误就近显示，提交后焦点进入第一个错误字段或错误摘要。

### 5.3 语气

- 使用主动、具体、短句：“保存任务”“打开工作台”“重新选择文件”。
- 数量使用阿拉伯数字；日期和时间使用本地格式化函数，不手写不一致的格式。
- 不用“系统异常”“操作失败”作为唯一信息；必须给恢复路径。
- 不用颜色单独传递“完成、逾期、危险”等状态。

### 5.4 术语表

同一概念只允许一种说法，动作词与状态词分开使用：

| 概念 | 唯一说法 | 避免 |
| --- | --- | --- |
| 从列表移除但可恢复的任务 | 移入回收站 | 删除、移除 |
| 不可恢复的任务删除 | 永久删除 | 删除 |
| 未安排日期的任务归处 | 收集箱 | 未分类、收件箱 |
| 任务没有计划日期 | 无计划日期 | 无时间、未安排 |
| 有计划日期但没定时间 | 无时间 | 无计划日期 |
| 任务所属的组织单元 | 列表 | 分类、分组 |
| 跨列表的属性 | 标签 | 分类 |
| 正常结束的任务（状态） | 已完成 | 完成 |
| 用户主动放弃的任务（状态） | 已取消 | 取消 |
| 回收站里的任务（状态） | 已删除 | 移入回收站 |
| 快速新增后的回退 | 撤销创建 | 删除 |
| 删除资料对话框 | 删除资料 | 确认 |

- 动作按钮使用动作词，状态标签使用状态词，两者不得混用。
- 修改术语时必须同步更新本表、相关测试断言与页面文案。

## 6. 响应式与主题

### 6.1 窄屏

- 目标验收宽度为 `390px`，核心流程不得横向溢出。
- Dashboard 侧栏转为顶部导航，快速记录改为纵向分组，任务行保持可操作高度。
- 抽屉和表单对话框使用可用全宽，主体内部滚动；不把关键字段隐藏到不可发现的区域。
- Toast、菜单和固定操作不能覆盖当前焦点或底部提交区域。
- 密度视图（例如月历格）也必须保留完整的任务操作入口：宁可让触发按钮占一点格子宽度，或改为点击任务行打开同一份“更多”菜单，也不得用 `display: none` 直接移除。
- 不通过缩小字号解决空间问题，优先调整布局和信息密度。

### 6.2 深色主题

- 使用 `color-scheme: dark`，原生滚动条、输入框、日期选择器和下拉列表必须跟随主题。
- 深色背景、表层、文字、边线和语义色都使用 `tokens.css` 的成对令牌。
- 检查 Toast、危险按钮、焦点环和遮罩在深色背景上仍有足够对比度。

### 6.3 离线与性能

- 运行时不依赖网络、第三方 CDN、远程字体或图标服务。
- 大列表避免在每次输入时做昂贵的全量布局读取；布局由 CSS Grid/Flex 处理，不用 JavaScript 测量位置。
- 任务标题、资料名称和错误文本必须处理长内容，允许换行、截断或折行，不得撑破容器。

## 7. 无障碍与交互验收

- 使用语义化 `header`、`nav`、`main`、`section`、`button`、`label`、`dialog`，不要用可点击的 `div` 或 `span` 代替按钮。
- 每个表单控件有可见标签、包裹标签或有意义的 `aria-label`；icon-only 按钮必须有 `aria-label`。
- 所有交互控件有清晰的 `:focus-visible` 焦点环，不能用 `outline: none` 隐藏焦点。
- 异步结果、Toast 和校验信息使用适合的 live region；不会因为颜色或动画才可理解。
- Tab 顺序遵循当前页面的阅读顺序；弹窗打开后焦点不逃出浮层，关闭后回到触发元素。
- Enter 提交主要表单，Esc 取消/关闭，按钮和选择控件同时支持鼠标、触摸和键盘。
- 控件使用 `touch-action: manipulation`；交互目标不低于产品统一的最小高度。
- 200% 缩放和 390px 宽度下仍能完成记录、完成、延期、删除和关闭弹窗。
- 减少动效时关闭非必要动画，不影响状态变化和操作反馈。
- 声明复合 ARIA 角色（`grid`、`listbox`、`menu`）时必须实现对应键盘交互：方向键在行/列/项之间移动，Home/End 到首尾，Esc 退出；没有实现就不要声明该角色。
- 页面级容器不使用 `aria-live`；只放在会变化的局部（结果、校验、列表数量），避免换页时整段播报。
- 同一屏内不允许出现两个可访问名称相同的按钮：同一个任务标题同时出现在“下一步”摘要和任务行时，摘要按钮使用动作名称（例如“下一步任务”），任务行按钮保留标题。
- 需要补充语义时优先在按钮外表达（区域标题、`aria-describedby`）；确要覆盖按钮名称时，必须保证不丢掉用户需要的动作或对象信息。

## 8. 设计决策清单

新增组件前必须回答：

1. 这是用户当前必须完成的动作，还是可以渐进披露的辅助信息？
2. 它属于 Popup、抽屉、确认框、表单对话框、Toast 还是普通页面内容？
3. 用户失败或误操作后如何恢复？是否需要撤销或二次确认？
4. 键盘、读屏、窄屏、深色主题和长文本下是否仍然可用？
5. 是否引入了重复卡片、重复文案、额外颜色或不必要的浮层？
6. 是否复用了 `tokens.css` 和现有组件语义，而不是新增一套局部规则？

## 9. UI/UX 交付验收

每次涉及界面或交互的修改至少验证：

- 2 秒内能找到当前页面主任务和快速记录入口；
- Popup 标题输入到保存只需输入和一次 Enter；
- Toast 不遮挡输入、日期按钮、快速记录、底部操作和当前焦点；
- 删除、覆盖、永久删除和高风险操作都有产品内确认或可恢复路径；
- 弹窗长内容在视口内滚动，Esc、取消和关闭按钮行为一致；
- 空、加载、错误、成功和冲突状态都有明确文案和下一步；
- 颜色、图标和动效都不是唯一的信息来源；
- 390px、200% 缩放、深色主题和键盘流程无横向溢出或焦点丢失；
- 术语与 5.4 节的术语表一致，动作按钮和状态标签使用同一套唯一说法；
- 页面级空状态都使用 `.empty-state` 结构，同一屏不出现两处空状态；
- 声明复合 ARIA 角色的页面可用方向键完成基本导航（例如月历切换日期）；
- 390px 下月历等密度视图仍可完成、延期和删除任务；
- 表单校验错误出现在字段或表单旁，而不是只闪过全局提示；
- 抽屉存在未保存修改时，关闭前有确认；
- 运行时无外部请求、无控制台未处理错误，且现有单元/E2E 测试继续通过。

实现冲突时，优先保证用户任务流、可恢复性和可访问性，再处理视觉装饰；所有调整都应回写本规范或 README 的相关说明。
